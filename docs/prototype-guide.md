# プロトタイプ確認ガイド

現在の開発版：`0.2.0-dev.5`。ブランチ：`develop/staged-ui`。確定済みのリリース版はmasterの`0.1.0`。

## 開き方

`npm ci`のあと`npm run dev`で起動し、表示されたURLを開く。通常は`http://127.0.0.1:5173/`。モデルをドロップすると自動処理し、保存ボタンから加工済みVRMを取得できる。

D&D待ち（処理中を含む）と結果・プレビューの2段階を、同じ画面内で切り替える。変換完了後にモデルと52個のスライダーを自動表示し、同じ画面の「VRMを保存」から加工済みファイルを保存できる。「別のファイルを変換」で最初に戻れる。

スライダーで単独・複合表情を操作でき、「すべてリセット」で中立に戻せる。マウスで回転・拡大も可能。まずJawOpen、EyeBlinkLeft／Right、MouthSmileLeft／Right、TongueOutを確認する。補足説明は「変換についての補足」を開いて確認する。

プレビューの読み込み中や失敗時にも保存できる。失敗時は「プレビューを再試行」が表示される。別ファイルへ戻るとプレビューと調整値を破棄し、読み込み中の古いモデルも表示しない。

モデル本体は端末内のWeb Workerで処理する。取得する供体テンプレートとアプリも同一配信元に配置し、プレビュー時も外部CDNに依存しない。3D処理が重い場合でも、変換後ファイルは先に保存できる。

## 現時点の結果

ローカル10モデルのうち8モデルに52個のPOSITION・NORMAL変形とVRM表情定義を追加できた。変換済みサンプルは`_local/output/`。元モデルと生成物はGit管理外。

| 対象 | 結果 |
| --- | --- |
| utageのVRM0／VRM1、JOUSHI1、bukao、client1、obasan1、sachiusuko、woman1 | 52表情追加、再変換で追加なし |
| 6493143135142452442 | 顔UVが供体と不一致のため停止 |
| ossan1 | 顔と身体が同じmeshに結合されているため停止 |

対応8モデルは、元ファイル・出力ともKhronos glTF Validatorのエラー0件、追加の警告0件。検証結果の詳細はローカルの`_local/validation.json`に保存する。

変換と再変換を合わせたNode.jsの処理時間は、今回の環境・約14〜22 MiBの対応入力で約0.3〜0.5秒。ブラウザーや他端末の性能保証ではない。

回帰検証は5項目（両VRM形式の追加・元BINや材質とメタ情報保持・再変換、破損GLB／範囲外accessor、sparse、既存表情の衝突）。Chromeの操作検証は6項目（両VRM形式の変換／保存／52スライダー、非対応から再試行、ローカルモデルの配信拒否、キャンセル、モバイル配置／不正ファイルのドロップ）。通信検証では同一配信元以外へのHTTP通信・GET以外のリクエストなし。Blob／data画像は端末内で利用する。

## 変換方式と制約

hinzka氏の女性供体の52表情Clipを、補助targetとweightも含めて事前に合成している。供体のモデル全体・テクスチャ・メタ情報は配信せず、約3 MiBの基準顔と変位を配信する。出所・供体hash・取得時の利用条件は`public/templates/`に保存。

顔パーツを材質名とVRM表情参照から識別し、UV対応を検証する。顔皮膚と口内の三角形構造も照合する。重複UVは近傍UVと顔皮膚から推定した軸別の座標補正で区別し、曖昧なら停止する。単に頂点数や番号が同じという判定ではない。

顔の各軸に沿ったスケール・向き補正を使う簡易転写であり、局所的な顔形状差の補正は未実装。NORMALは変形前後の幾何法線差から追加し、元の法線を保持する。接線の再計算は未実装で、法線マップを利用する入力等の見え方は追加確認が必要。唇・歯・まぶた・舌の干渉や複合表情の品質はユーザーによる確認を要する。

安全に扱える範囲から始めるため、部分的にPerfect Sync表情が既にあるモデル、顔のweights animation、顔nodeの明示的な座標変換、未知の必須extension、外部バッファ／画像、一部の圧縮形式、未知GLBチャンク等は停止する。対応範囲を広げる際に個別に検証する。

元BINと既存indexを保持して差分を追記する。VRM0の表情はPascalCase名・weight=100、VRM1もPascalCaseのcustom名・weight=1。Morph Target名はlowerCamelCase。出力形式は入力と同じで、VRM1→0の変換は行わない。

設計のReact／TypeScript案に対し、今回のPoCは依存と初期作業を抑えるためVite＋JavaScriptの小さな画面・共有エンジンで実装した。UI拡張時に型付けやフレームワーク導入を見直す。

## 利用先での確認

WebcamMotionCaptureを主な検証先とする。まず出力VRMを読み込み、表情名の認識、左右、まばたき、口内・舌、既存の母音や感情との同時適用を確認する。使用したアプリ版と入力ファイル・結果を記録する。

VSeeFaceはVRM0の補助確認に利用できる。VRM1は対応しない。Perfect Syncの実際のトラッキング品質を確認する際は、対応するトラッキング入力も必要。アプリが無料であることは、トラッキング入力の準備を不要にする意味ではない。

この環境で実施済みなのはブラウザーでの表示・スライダー操作とファイル検証まで。WebcamMotionCapture／VSeeFaceによる実機確認は未実施。

## Cloudflare公開準備

Cloudflare Pagesではビルドコマンド`npm run build`、出力ディレクトリ`dist`を指定する。すべて静的ファイルであり、変換用APIやモデル保存用ストレージは不要。`public/_headers`に配信用ヘッダーを置いている。`_local/`がdistに含まれないことも確認する。

この段階ではデプロイしていない。0.1.0はユーザーの了承によりリリース版に確定。GitHubリポジトリが未作成のため、今回の明示指示に従ってPRを作成せずローカルmasterに直接マージする。

## 公開前チェックで追加した入力制限

入力GLBは100 MiB、JSONは16 MiB、accessor全体は8,388,608成分まで。顔primitiveは64個まで、各primitiveの頂点は50,000個、indicesは300,000個まで。変形追加後のBIN推定が100 MiBを超える場合は停止する。ブラウザーでの変換は120秒で停止し、選び直しができる。これらはブラウザーの総メモリー使用量を保証する上限ではない。

外部画像・外部バッファを拒否し、プレビューのローダーも埋め込み画像用blob以外の参照を拒否する。accessorとbufferViewの整数・範囲・sparse参照を確認する。
