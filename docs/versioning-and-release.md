# バージョンとリリース方針

## ユーザー指定のルール

アプリケーションのバージョンは`<major>.<minor>.<fix>`の3フィールドで表します。

| 変更内容 | インクリメントする番号 |
| --- | --- |
| 大きな機能追加 | major |
| 小さな機能追加等 | minor |
| バグフィックス | fix |

一般的なSemantic Versioningの互換性基準ではなく、上記のユーザー指定を優先してください。

開発版は`<major>.<minor>.<fix>-dev.<revision>`とします。基本は開発版として進行します。revisionは厳密な全コミット数である必要はなく、開発の進行に応じて増える、おおよそのコミット回数に相当する番号とします。

## 開発開始時

開発版を始める際は、予定する変更内容に応じて、あらかじめmajor・minor・fixの該当フィールドをインクリメントしてください。リリース直前まで基底バージョンの更新を遅らせないでください。

運用上、major更新時はminorとfixを0に、minor更新時はfixを0に戻し、新しい開発版のrevisionは1から始めます。開発版のコミットごとにrevisionを増やすことを目安とし、番号更新だけの不要なコミットは作らず、該当変更と合わせて更新します。

例：リリース版が`1.2.3`の場合。

- 大きな機能追加：`2.0.0-dev.1`
- 小さな機能追加：`1.3.0-dev.1`
- バグ修正：`1.2.4-dev.1`
- 開発の進行：`1.3.0-dev.1`→`1.3.0-dev.2`→`1.3.0-dev.3`…

初回の基底バージョンは未指定です。初回実装時に作業内容に合わせて設定し、選定理由を記録してください。

## リリース手順

ユーザーが「問題がない」と判断した際に、次の手順を実施してください。

1. `-dev.<revision>`を削除し、同じ基底バージョンのリリース版にする（例：`1.3.0-dev.8`→`1.3.0`）。
2. バージョンを持つ関連箇所の整合性を確認し、必要な検証を行う。
3. リリース版への変更をコミットする。
4. リリース版のブランチをpushし、`master`を対象にPRを作成する。

ユーザーの判断前に、独自判断で開発版の接尾辞を削除しないでください。判断後のリリースコミットとmaster向けPR作成は、今回指定された手順として実施します。PRのマージ、タグ作成、デプロイはこの指示だけでは実施しません。
